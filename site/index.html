Process under Membership means the role can encode member applications. Approve means the role can convert approved applications into active members. In the current spike, System Administrator and Membership Officer can create member applications, System Administrator is the only role that can approve them, System Administrator and Membership Officer can preview mapped member CSV imports, Teller / Cashier records the initial member payment, and Accountant / Bookkeeper posts teller batch payments to the general ledger. Member Import Preview is discovery-only: pasted Excel/CSV rows are mapped and validated before any active member write is implemented. Member Import Staging saves mapped rows into an import batch review queue with ready and issue counts, but staged rows are not active member records yet. Member Import Finalize lets the System Administrator convert ready rows into active member profiles with zero share capital and zero savings. Opening Balance Import Planning lets the System Administrator and Accountant / Bookkeeper preview mapped cutover balances before any balance write exists. The Ledger workspace is organized into role-aware tabs for Batch Review, Opening Balances, Batch History, and Posted Entries so users open one ledger work area at a time. Opening Balance Import Staging saves mapped cutover rows into a staged review batch, flags duplicate or already-staged member numbers and other validation issues, and does not change balances until a later finalization step. Admin and Bookkeeper can open staged batch details to review row issues and raw source values. Admin may reject a batch while retaining it as audit evidence and allowing a corrected upload for the same members. Admin can finalize ready rows after confirmation, applying share capital and savings amounts to member balances while issue rows remain skipped. Finalized batches retain actor and timing evidence and cannot run twice. Finalization now creates one balanced journal: debit Opening Balance Clearing, credit Share Capital, and credit Savings Deposits Payable. The journal is linked to the batch and appears in Posted Entries and reports. Older finalized batches without this linkage can be repaired by the System Administrator. Member Statements now show finalized opening balances with their batch, cutover date, source reference, and journal number. Member Subsidiary Ledger separates opening share capital and savings from normal transaction movements. Loan Product Foundation replaces the Loans placeholder with reusable Regular, Emergency, and Small Business loan templates. Admin maintains amount and term limits, rates, fees, penalties, status, and accounting mappings. Manager, Loan Officer, Credit Committee / Approver, Teller / Cashier, and Auditor have read-only product access. Loan Application v1 adds a separate Applications tab. The Loan Officer can create and edit their own Draft, with active-member checks and product amount and term limits enforced. Product rates, methods, fees, penalties, and accounting mappings are copied into the application as an audit snapshot. Submitting makes the record read-only and visible to Admin, Manager, Credit Committee / Approver, and Auditor. Loan Credit Review lets the Credit Committee / Approver record assessment notes, recommended amount and term, decision date, and remarks before choosing Approved, Rejected, or Returned. Returned applications go back to the originating Loan Officer for revision and resubmission. Approval cannot exceed the member's request, and decided applications are immutable. Loan Computation and Amortization Preview adds a separate Computations tab. The originating Loan Officer selects the first payment date, previews the Flat Interest schedule, processing fee, net proceeds, total payable, and maturity, then saves it once as For Release. Whole-peso rounding differences go to the final installment. Loan Release v1a adds a Releases tab for Teller / Cashier. Teller verifies the computed amounts, enters a unique voucher and release date, and confirms cash equal to net proceeds. The release is immutable, linked to the Open teller batch, and counted as cash-out. Loan Release v1b lets Bookkeeper post the Reviewed batch: debit Loans Receivable for principal, credit Cash for net proceeds, and credit Processing Fee Income for the fee. The release and loan become Posted and retain their linked journal number. Teller Cash Funding v1a establishes custody before payouts. Bookkeeper prepares funding from an identified source, Manager approves it, and the assigned Teller acknowledges it into the Open batch. Expected ending cash is Opening Funding plus receipts minus payouts, and batch details retain all three control actors. Initial member payment is one-time only; later member activity uses the normal savings deposit, savings withdrawal, or share capital contribution workflows. Cash-in OR/reference numbers cannot be reused across initial payments, share capital contributions, and savings deposits, and withdrawal voucher/reference numbers cannot be reused across withdrawals. Teller / Cashier can submit actual cash counted for the unposted batch, while Accountant / Bookkeeper reviews expected cash, actual cash, and variance before posting. The implemented batch status flow is Open to Submitted to Reviewed to Closed, then the next teller batch opens for new activity. Posting is allowed only after review. Bookkeeper posts the reviewed batch in one action, while the system keeps source-level journal entries for audit traceability. Non-zero variance requires a Bookkeeper variance note before review. Official close records closed by, closed time, and optional closing note. Teller Batch History remains available as read-only evidence after closing, and each row can be opened to inspect cash count evidence, transactions, and linked journals. Reports now use a selector layout so users open one report at a time. Daily Cash Position summarizes teller batch cash evidence in Reports. Member Subsidiary Ledger summarizes member share capital and savings balances in Reports. Control Account Reconciliation compares prototype activity subsidiary totals to GL controls. Trial Balance summarizes posted GL debit and credit totals and flags whether the ledger is balanced. Statement of Financial Condition presents assets, liabilities, and equity from posted ledger balances. The Members workflow auto-refreshes every 5 seconds during demo testing, with a manual Refresh button available when users want the latest state immediately. The Members screen is now organized into role-aware tabs for Applications, Imports, Teller Transactions, Member Directory, and Transaction History.

Operating flow

Core Cooperative Workflows

Member Application

  1. Membership Officer encodes application.
  2. Required Initial Share Capital is reviewed.
  3. Application is submitted for approval.
  4. System Administrator approves membership.
  5. Teller collects initial share capital, membership fee, and savings.
  6. Admin or Membership Officer maintains member profile master data.
  7. Admin or Membership Officer can preview mapped Excel/CSV member imports.
  8. Admin or Membership Officer can stage mapped import rows for review.
  9. System blocks duplicate initial member payments for the same member.
  10. System blocks reused cash-in OR/reference numbers.
  11. Transaction remains in teller batch until accounting posting.

Teller Transaction

  1. Teller selects active member account.
  2. Member statement shows share capital, savings, and posting status.
  3. Teller chooses one transaction type in the workspace.
  4. Share capital contribution is available after onboarding.
  5. Selected transaction is encoded and validated.
  6. System blocks reused OR or voucher reference numbers.
  7. Receipt is issued.
  8. Cash in, cash out, net cash, and transaction counts are summarized.
  9. Teller submits actual cash counted and system computes variance.
  10. Bookkeeper records a variance note when the cash count has non-zero variance.
  11. Bookkeeper marks the submitted teller batch as reviewed.
  12. System allows posting only after the batch is reviewed.
  13. Bookkeeper posts the reviewed teller batch in one action.
  14. Bookkeeper confirms official close after its transactions are posted.
  15. System keeps read-only batch history for audit review.
  16. Batch history rows can be opened for cash count, transaction, and journal details.
  17. Reports summarize daily cash position from teller batch evidence.
  18. Reports summarize member subsidiary balances for share capital and savings.
  19. Reports compare subsidiary activity against GL control accounts.
  20. Transaction stays in teller batch until posting.

Loan Application

  1. Loan Officer selects an active member and active loan product.
  2. System validates requested principal and term against product limits.
  3. Loan Officer saves and may edit their own Draft.
  4. Loan Officer submits the Draft, making it read-only.
  5. Credit Committee / Approver records assessment notes and a decision.
  6. Returned applications go back to Draft for Loan Officer revision.
  7. Approved and Rejected applications retain immutable decision evidence.
  8. Loan Officer previews and saves the approved amortization schedule.
  9. Saved computations move to For Release without moving cash.
  10. Bookkeeper prepares Teller funding and Manager approves it.
  11. Assigned Teller acknowledges funding into the Open batch.
  12. Teller confirms the unique release voucher and exact net cash proceeds.
  13. Released proceeds enter the Open teller batch as cash-out evidence.
  14. Bookkeeper reviews the batch and records any required variance note.
  15. Posting creates the balanced loan release journal and linked evidence.

Ledger Posting

  1. Teller payment remains in Teller Batch status.
  2. Bookkeeper reviews the supporting transaction.
  3. Balanced entries are posted to Cash, receivables, capital, income, and deposit controls.
  4. Opening balance imports are previewed separately before any cutover balance write exists.
  5. Reports are generated from posted ledger entries.

Persistence

Demo Reset Safety

The working app can remain in in-memory seed mode while DATABASE_URL is blank. When Postgres is configured, demo data can be restored with a reset command that creates a JSON backup before reseeding the configured database. The hosted Render demo also includes an admin-only Demo Maintenance panel for backups and typed-confirmation resets.

Render free deployments require manual schema migration from a local terminal before code with new database columns is deployed. The health endpoint reports schema status so missing columns can be caught early. Member Import Staging adds Postgres tables for import batches and import rows, so run the migration before deploying that app build. Member Import Finalize adds finalization columns to import batches, so run the migration before deploying that app build as well.

The System Administrator can create prototype staff users, assign roles and default screens, and deactivate non-admin accounts while the prototype still uses one shared test password. The Auditor / Compliance Officer can review usernames, roles, default screens, and account status through a read-only User / Security directory without password, maintenance, backup, or reset access.
